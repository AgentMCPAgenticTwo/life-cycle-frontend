# Frontend — repo conventions

This file is the contract for anyone (human or agent) writing code here. It is generated by
the ui-dev-agent from each run's tech stack and module contract, and refreshed on every run.

Sections wrapped in `<!-- STACK:... -->` and `<!-- MODULE:... -->` markers are generated —
do not hand-edit inside them. Edits outside the markers are preserved across runs.

## Stack

- Frontend: **React** (javascript)
- Backend: **Python · FastAPI** (python)
- Database: **PostgreSQL**

## Dependencies

Use only what is already declared in this repository's manifest. Do **not** add dependencies. If a UI primitive is missing (tabs, dialog, dropdown, select, chips), write it by hand next to the other shared components.

## Layout

```
src/pages/<ScreenName>.tsx        route-level screens, one per screen
src/features/<feature>/           components and hooks specific to one feature
src/shared/components/ui/         reusable primitives (button, input, dialog, ...)
src/shared/components/            reusable app-level components
src/shared/types/                 domain types — the TypeScript side of the API contract
src/services/                     typed API clients over http.ts
src/store/                        zustand slices
src/__tests__/                    screen-level tests
```

Import with the `@/` alias (`@/shared/components/ui/button`), never deep relative chains.

# API layer.

- Every network call goes through the shared client in `src/services/http.ts`. Feature code
  never calls `fetch` directly.
- The backend base URL comes from `VITE_API_BASE_URL` (set it in `.env.local`; see `.env.example`).
  It is required — the client throws at startup when it is missing rather than falling back
  to sample data.
- The client attaches `X-User-Role` and `X-User-Id` to every request and converts any
  non-2xx response into a thrown `HttpError` carrying the API's `{ error, details }` body.
- One service module per resource group, named after that resource in this contract, typed
  with the DTOs listed in the module sections below and calling exactly those paths.
- Multipart endpoints send `FormData`; never set `Content-Type` by hand for those.


# Tests.

Vitest + Testing Library. Test files use `*.test.tsx` and sit next to the unit they test;
screen-level tests go in `src/__tests__/`. Mock `src/services/http.ts` in tests — that is
the one place fake data is allowed.

## Checks — all must pass before you call a task done

```bash

```

## No mock data — every screen is wired to the real API

This repo does **not** use mock data, dev fallbacks or fixtures in feature code:

- Do **not** add a dev-fallback wrapper, a mock-data module, an "if development" data
  branch, a hard-coded sample array, or any "return fake data on error" path. If you find
  one, remove it and wire the real endpoint.
- A service function calls the API and **returns the typed response or throws**. Errors
  reach the screen's error state; they are never swallowed or replaced with placeholders.
- Every data-bound screen implements four states driven by the real request: **loading**,
  **empty** (2xx with no rows — show the spec's empty message), **error** (non-2xx or
  network failure — show the message with a retry), **populated**.
- Dropdown/filter options come from real lookup endpoints, never inline constants.
- Sample values are allowed **only** inside test files.
- If the backend base URL is not configured, fail loudly at startup rather than falling back
  to mock data.

## Talking to the backend

- Every request carries the `X-User-Role` and `X-User-Id` headers, attached centrally by the
  shared HTTP client. A missing header is **401** and a disallowed role is **403** — both
  must surface in the UI's error state, not crash the screen.
- Non-2xx responses share one body shape: `{ "error": string, "details": string[] }`. Show
  `error` to the user; `details` carries field-level messages.
- Paged endpoints take `page`/`pageSize` (plus `search`/`sortBy`/`sortOrder` and filters) and
  return a paged envelope with `items` and the total count.
- Use exactly the paths, methods and field names listed in the module sections below.
  **Never invent a URL or a field name** — the backend implements the same contract, so a
  renamed field is a 200 response with blank fields on screen, not an error.

## Adding a module without breaking the last one

Each generated module section below is one module. When you implement a new module, **add**
files alongside the existing ones — do not delete, rename or rewrite screens, services or
types belonging to a module you were not asked to touch. Shared code may be extended, not
narrowed. If a change to shared code would break an existing module, keep the old behaviour
and add the new path beside it.

## Identifiers -- the same format on both sides

Ids in this project are **UUIDs**. Every id field -- path parameters, request bodies, response bodies, foreign keys -- is a UUID string such as `00000000-0000-0000-0000-000000000001`.

- Never send a human-readable key (`USR-0001`, `JOB-42`, `ORD-7`) where a UUID is expected. The database rejects it at the driver, not at validation, so it surfaces as `invalid input syntax for type uuid` -- a 500, not a 400.
- Ids are **generated by the backend**, never by the frontend. On create, POST the
  body *without* an id and read the id off the response.
- Never hard-code a specific id, and never invent a sample id in feature code. Ids
  come from a previous response, from route params, or from the user's selection.
- The frontend's typed models and the backend's DTOs declare id fields with the same
  name and the same type. If they disagree, the contract wins.

## Auth headers

Every request carries `X-User-Role` and `X-User-Id`, attached centrally by the shared
HTTP client -- never per call site.

- Roles this contract defines: TENANT_ADMIN, CONTRACT_OWNER, LEGAL_REVIEWER, APPROVER, SIGNER. Use exactly these spellings; a role outside
  the set is a **403**, and a missing `X-User-Role` is a **401**.
- The scaffold's dev identity (`TENANT_ADMIN` / `00000000-0000-0000-0000-000000000001`) is a
  placeholder for an environment with no login flow. It is a starting value, not a
  fact about the domain -- replace it with the signed-in user once real auth exists,
  and never copy it into feature code or seed data as though it were a real record.
- `X-User-Id` must be in the id format above: the backend looks it up as a real key.

## Request bodies must carry every field the contract declares

When you POST or PUT, send **every** field the request DTO lists -- not just the ones
the form happens to render. A field the backend requires and the client omits is a 400
at best and a silently-null column at worst. Match names and casing exactly, and do
not add fields the DTO does not declare.

## Codebase knowledge (OKF)

This repository keeps a codebase knowledge graph and an agent-readable knowledge
bundle generated from it. Both are refreshed by the sage-maintenance workflow at
the end of every maintenance run -- read them before exploring the code.

- **Graph:** `.codebase-memory/graph.db.zst`, served by the codebase-memory-mcp
  MCP server as project `life-cycle-frontend`. Prefer `search_graph`, `trace_path`,
  `get_code_snippet`, `get_file_outline` and `get_architecture` over grepping or
  reading whole files.
- **Bundle:** `.knowledge/`, in Google's Open Knowledge Format (OKF) v0.2.
  Start at `.knowledge/index.md`.

### Rules for writing `.knowledge/` -- always follow these

Whenever you create or update any file under `.knowledge/`, write it in
OKF v0.2 exactly as below.

1. The bundle is a directory of markdown files. `index.md` and `log.md` are
   reserved at every level; every other `.md` file is one **concept**.
2. Every concept file starts with a YAML frontmatter block between `---` lines.
   `type` is REQUIRED and non-empty. Also write `title`, `description` (one
   sentence), `tags`, `resource`, `generated`, `sources` and `status`:

   ```yaml
   ---
   type: Module
   title: components/hero
   description: Scroll-driven hero section that renders a canvas frame sequence.
   resource: https://github.com/<org>/<repo>/tree/<default-branch>/components/hero
   tags: [frontend, hero]
   generated: { by: sage-maintenance/claude-code, at: 2026-01-01T00:00:00Z }
   sources:
     - id: cbm-graph
       resource: codebase-memory-mcp project life-cycle-frontend @ <commit sha>
       title: Codebase knowledge graph
   status: stable
   ---
   ```

3. Concept types: `Codebase Overview`, `Architecture`, `Convention`, `Module`,
   `Playbook`, `Reference`. Every timestamp is ISO 8601 UTC with a `Z`.
4. Layout:

   ```
   .knowledge/
     index.md                    # bundle root index
     log.md                      # update history
     overview.md                 # type: Codebase Overview -- purpose, stack, scripts, entry points
     architecture.md             # type: Architecture -- clusters, layers, boundaries, hotspots, call/render tree
     conventions.md              # type: Convention
     modules/index.md
     modules/<module-slug>.md    # type: Module -- one per source package/directory (at most 40)
     playbooks/common-tasks.md   # type: Playbook -- "to change X, go to Y"
     reference/graph-queries.md  # type: Reference -- how to query the live graph
   ```

5. `index.md` files carry NO frontmatter, except the bundle-root `index.md`,
   whose frontmatter is only `okf_version: "0.2"`. The body is `# Heading`
   sections of `* [Title](path) - description` entries, using each concept's own
   `description`.
6. `log.md` carries no frontmatter: `# Knowledge Update Log`, then `## YYYY-MM-DD`
   groups, newest first, with entries such as `* **Update**: ...` or
   `* **Creation**: ...`. Add new entries at the top; never rewrite old ones.
7. Link concepts with bundle-absolute markdown links, e.g.
   `[Hero](/modules/components-hero.md)`. The links are the knowledge-graph
   edges; state the relationship in the prose ("depends on", "rendered by").
8. Bodies use headings, tables and lists rather than long prose. Every file path
   and symbol you name must exist in the graph.
9. When updating a concept, keep human edits and any `verified` entries. When
   the code a concept describes is removed, set `status: deprecated` rather than
   deleting the file.
